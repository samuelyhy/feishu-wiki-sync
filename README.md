# feishu-wiki-sync

把本地 Markdown 按**文件名**同步到飞书知识库中的**同名文档**，做**块级增量更新**。

- 文档 **URL 不变**（保留知识库节点 `node_token`）
- **未改动的块保留原 `block_id`**，挂在块上的评论不丢
- **改动过的块走原地更新**，评论同样保留
- 重复执行零副作用

```
pnpm install      # 会通过 prepare 钩子自动构建
pnpm build
node dist/bin/cli.js --help
```

## 安装

**本仓库用 pnpm**（仓库内只保留 `pnpm-lock.yaml`，请勿用 npm 安装依赖以免生成第二份 lockfile 造成依赖树漂移）。

工具本身可被任何包管理器安装，三种方式都实测可用：

```bash
# ① 全局安装（pnpm，推荐）—— 之后在任何目录直接敲 fws
cd <本项目目录>
pnpm add -g .
# 若报 "global bin directory is not in PATH"，先执行一次：
pnpm setup && exec $SHELL

# ② 全局安装（npm）—— 打包快照，复制到全局目录
npm install -g .

# ③ 软链（改完代码 build 一下即刻生效）
pnpm link --global     # 或：npm link
```

三者的区别：

| 方式 | 行为 | 适合 |
|---|---|---|
| `pnpm add -g .` | **软链**到源码目录 | 本机开发自用，改完 build 即生效 |
| `npm install -g .` | **打包快照**，复制到全局目录 | 固定版本使用 |
| `pnpm link --global` / `npm link` | 软链 | 同 `pnpm add -g .` |

安装会同时提供两个命令名：`fws` 与 `feishu-wiki-sync`。

**装完先自检**：

```bash
fws --version     # 应输出版本号
fws --help
```

> **打包与构建**：`bin` 指向 `dist/` 下的编译产物，所以 `package.json` 里配了 `prepare` 与 `prepack`
> —— 从干净的 clone 安装时会自动构建，不需要先手工 `pnpm build`。
> 这也是为什么 `dist/` 虽然被 gitignore，全局安装却仍然可用。

> **想发到内部 registry 供团队安装**：需要先去掉 `package.json` 里的 `"private": true`
> —— npm 会拒绝发布任何标记为 private 的包（但它**不影响**从本地路径做全局安装）。

```bash
# 1) 建飞书自建应用，拿 App ID / Secret
# 2) 配置凭证与知识空间，并列出可选父节点
fws init --app-id cli_xxx --app-secret xxx --space-id 7524xxxxxxxx

fws doctor --write              # 含写入链路（会创建一篇可手工删除的验证文档）

# 4) 只读看看现状
fws status --verbose

# 5) 先演练，确认变更清单符合预期
fws sync --dry-run

# 6) 正式同步
fws sync
```

## 前置条件（最容易卡住的地方）

**权限是双重的，两把锁都要开，缺一条全程报 `131006`。**

1. **API scope**：在开发者后台为应用开通
   - `docx:document`（创建与编辑新版文档）
   - `docx:document.block:convert`（Markdown 转块）
   - `wiki:wiki`（查看、编辑和管理知识库）
   - `drive:drive`（素材上传）
   - 开通后**必须发布应用版本**，权限才生效

2. **资源成员身份**：
   - 在飞书里建一个群 → **把应用作为机器人加进群**（必须是**应用机器人**，群自定义机器人不行）
   - 到知识库「成员设置」→ 把**这个群**加为**管理员**或成员

应用调用的 API 计入飞书调用量配额（免费版 **100 万次/月**）。文档/drive/wiki 类接口全部计入。

## 部署前体检：`fws doctor`

这个工具的若干关键逻辑建立在**无法从官方文档确证**的行为上。在拿到真实凭证之前，这些只能被标成「未确认」——而「未确认」在实践中等于「上线后才发现」。

`fws doctor` 把每一条假设变成一次真实调用 + 一句判读：

```bash
fws doctor --verbose     # 只读，逐项报告在验证什么
fws doctor --write       # 追加写入链路验证
```

| 检查项 | 验证的假设 | 失败通常意味着 |
|---|---|---|
| 配置 | — | 配置本身有问题 |
| 凭证 | `tenant_access_token` 能否获取 | App ID/Secret 错，或应用**未发布版本** |
| 知识空间 | `space_id` 可达 | space_id 抄错，或应用不是空间成员 |
| 父节点 | 每个 mapping 的父节点存在且可写 | token 过期，或权限双门禁只开了一半 |
| 转换 | `convert` 的返回结构；**远程图片是否生成 Image 块** | 缺少 `docx:document.block:convert` scope |
| 写入链路 | **`tenant_access_token` 能否真正写入知识库** | 见下方说明 |

### 最该关注的一条：写入链路

社区有实践记录称 **`tenant_access_token` 根本写不了知识库、必须用 `user_access_token`**；而飞书官方文档说除「创建知识空间」与「搜索 Wiki」外，Wiki 接口**均支持** tenant token。两个来源冲突，只能在真实租户上判定。

`fws doctor --write` 就是那把尺子。它会：

1. 在第一个 mapping 的父节点下创建一篇名为 `[fws doctor] 可删除的验证文档` 的节点
2. 写入内容并读回验证
3. 报告结果

> ⚠️ **飞书没有删除知识库节点的 API**，所以验证文档需要**手工删除**。这也是它默认不开启（要显式加 `--write`）的原因。
>
> 若这一项失败而其他项都通过，说明「应用是空间成员」这个前提没被满足 —— 先检查权限双门禁。若权限确认无误仍失败，才需要考虑改用 `user_access_token`（那会引入 OAuth 与 365 天重授权问题）。

### 关于 `convert` 检查

它会用一份覆盖全部支持语法的样本调一次 `convert`，然后报告：

- **图片块数与全部图片引用数相等** → 远程图片**会**生成 Image 块，配对适用于全部引用
- **图片块数只与本地图片引用数相等** → 远程图片**不**生成块，配对只在本地图片之间进行

两种代码都能正确处理（同步时自适应选配对列表）。这一项的用途是**告诉你是哪一种**，避免哪天出现错位时无处可查。

## 配置

两层，凭证与映射分离。

**`.ai-sync.env`**（自动写入 `.gitignore`，绝不入库）

```bash
FEISHU_APP_ID=cli_xxxxxxxxxxxx
FEISHU_APP_SECRET=xxxxxxxxxxxxxxxxxxxx
```

**`.feishu-sync/config.yaml`**（可入版本控制，无密钥）

```yaml
version: 1
space_id: "7524100000000000001"

defaults:
  include: ["**/*.md"]
  exclude: ["**/releases/**", "**/*.draft.md"]
  on_missing: create       # 远端无同名文档时：create 新建 | fail 报错
  # on_ambiguous 只支持 fail（同名多个时停下问人），可不写

mappings:
  - source: docs/specs
    parent_node_token: "wikcnSPECSxxxxxxxx"

  - source: docs/guides
    parent_node_token: "wikcnGUIDESxxxxxxx"
    exclude: ["**/_draft/**"]
```

**一个 `parent_node_token` 只能对应一个 `source`**，且两个 `source` 不能互相嵌套 —— 违反会让两份本地文件抢同一个远端文档，表现为两台机器互相覆盖且不报错。

> ⚠️ **`nesting: mirror`（镜像本地目录层级）尚未实现。** 配置里写了也不会报错，但行为仍是 `flat`
> —— 全部平铺在父节点下。子目录里的文档**不会**在知识库里对应出子节点。

### 认证方式

全程使用 `tenant_access_token`（应用身份），不走 OAuth。原因：`user_access_token` 的 refresh token 是一次性的，且**用户授权满 365 天必须重新授权**（报 `20037`），对无人值守的同步工具是不可接受的运维负担。

代价：知识库里显示的文档作者是机器人。

## 命令

| 命令 | 说明 |
|---|---|
| `fws init` | 采集凭证、生成配置骨架、把 `.ai-sync.env` 写进 `.gitignore` |
| `fws init --list-nodes` | 列出知识空间的顶级节点 |
| `fws init --check` | 联网校验空间可达、各 mapping 的父节点存在且应用有权限 |
| `fws doctor` | **体检**：逐项验证凭证、空间、父节点、转换链路（只读） |
| `fws doctor --write` | 额外验证写入链路（会创建一篇验证文档，需手工删除） |
| `fws status` | 只读，**完全离线**：哪些未认领 / 已改 / 未变 |
| `fws status --remote` | 额外检查远端是否被人改过（每篇 1 次读请求）；**发现漂移时退出码 3** |
| `fws pull` | **对比远端与本地**（git 语义）：本地新增 / 远端新增 / 本地领先 / 远端领先 / 冲突 |
| `fws pull --write` | 把远端领先/远端新增的文档写入本地 |
| `fws sync` | 执行同步 |
| `fws sync docs/specs` | 只同步指定目录（路径前缀匹配） |
| `fws sync docs/specs/01-domain.md` | 只同步单个文件 |
| `fws sync --cwd /path/to/project` | 指定工程根目录，不必先 `cd` 过去 |

### init 的开关

| 开关 | 语义 |
|---|---|
| `--app-id` / `--app-secret` | 飞书自建应用凭证，写入 `.ai-sync.env` |
| `--space-id` | 知识空间 ID |
| `--parent-node-token` | 写入配置骨架的目标父节点 |
| `--list-nodes` | 列出顶级节点 |
| `--check` | 联网验活 |

三个命令都支持 `--cwd` 与 `--verbose`；结构化的 `--json` 输出只有 `status` 与 `sync` 有（`init` 接 `--json` 只是把人类可读日志改道到 stderr）。

### sync 的开关

| 开关 | 语义 |
|---|---|
| `--dry-run` | 只扫描与比对，**不写入任何内容**（也不会创建节点） |
| `--force` | 覆盖「远端被人修改过」的文档；默认拒绝并跳过 |
| `--reclaim` | 忽略账本，重新按标题认领（用于账本损坏后重建；已同步的文档不会重复创建） |
| `--allow-destructive` | 授权破坏性变更（会清空远端 / 大幅删减 / 首次纳管非空文档）；默认一律拦截 |
| `--json` | 结果以 JSON 输出到 stdout（人类可读日志走 stderr） |
| `--verbose` | 逐文件详情 |

### 退出码

| 码 | 含义 | 该怎么做 |
|---|---|---|
| 0 | 全部成功（含「无变更」） | — |
| 1 | 有文档同步失败 | 重跑常能自愈 |
| 2 | 配置错误 | 改配置 |
| 3 | 需人工处理（同名歧义 / 冲突 / 远端漂移） | **必须人介入** |
| 4 | API 配额耗尽 | 本月别再跑了 |

3 优先于 1：失败重跑常能自愈，歧义放着不管会持续产生重复文档或覆盖错文档。

## 工作原理

### 为什么按名称匹配只用于「首次认领」

标题匹配失败是**静默的** —— 匹配落空会新建一篇重复文档，或者更糟，匹配到同名但属于别人的文档并覆盖它，全程不报错。

所以：**首次同步按标题认领，立刻把 `文件路径 → node_token` 写进账本，之后一律以账本为准。** 这条纪律不遵守，跑几周后知识库一定会乱。

同名文档有多个时默认停下报错（退出码 3），列出候选让你用 `--reclaim` / 手工 `aliases` 处理 —— 不自动猜。

### 为什么需要块指纹

`convert` 接口吃 Markdown 文本、吐的是**临时 ID**，本地 md 没有任何办法携带远端 `block_id`。所以「本地第 N 个块对应远端哪个块」**只能靠内容指纹对齐**。

指纹包含文本、元素级样式（加粗/链接/颜色）、块级样式（对齐、代码语言、缩进）、以及容器块的子块内容。两条纪律：

- **必须包含样式**，否则「给某个词加粗」会被判成没变而静默漏更
- **归一化必须保守**，归一化过度会造成「明明变了却判为没变」，比误报严重得多

代码块**不做空白折叠** —— 代码里的缩进有语义，折叠后两个不同片段会被判为同一个。

### 对齐与写入顺序

1. **LCS 精确匹配**（Hunt–Szymanski）找出未变的块 → 保留，一个请求都不发
2. 空隙中**等长且类型与样式逐个相同** → 配对为 `batch_update`，**`block_id` 不变，评论得以保留**
3. 其余整段替换

写入顺序是这里最容易做错的地方：

```
① 先做完全部 batch_update   —— 它按 block_id 定位，不改索引
② 变化段【倒序】处理，段内先删后插
```

因为 `batch_delete` 用**索引范围**、`descendant` 用**插入位置**，两者都会挪动后续块。先处理靠后的段，靠前段的索引才仍然有效。**顺序反了不会报错，只会把内容写到错误的位置上。**

### 变更检测

账本记录的是**正文 + 全部引用图片的合成哈希**，而不是正文哈希。只改图片不改正文时 Markdown 文本一字未动，但文档内容确实变了 —— 只看正文哈希会让这种情形被快路径判为「无变化」而永远同步不过去。

### 图片怎么对齐

Markdown 里的图片靠**位置**对应到文档里的 Image 块（第 N 个引用 ↔ 第 N 个块），因为 `convert` 不返回稳定 ID。

这条链条上有两个必须守住的点：

- **远程图片不能被过滤掉。** 抽取时若把远程图滤掉，它之后的每一张本地图都会前移一位、挂到别人的块上，而且**不报错**。所有图片引用都保留在列表里，远程图只是「不上传」。
- **数量对不上就报错。** 若抽取到的引用数与 `convert` 产出的块数**两种配对方式都对不上**（例如用了 HTML `<img>` 标签），直接失败并提示，而不是猜着配对。

围栏代码块里的 `![](x.png)` 是代码文本、不会生成 Image 块，因此抽取时会跳过围栏内的内容。

**配对方式是自适应的**：`convert` 会不会为**远程图片**也生成 Image 块，官方文档没有明说，所以代码两种都支持 —— 块数与「全部引用」相等就按全部配对，只与「本地引用」相等就只按本地配对。`fws doctor` 会告诉你实际是哪一种。

### 漂移保护

每次同步前比对远端 `revision_id` 与账本记录值，不一致说明有人在知识库里改过：

- 本地没改 → 报告 `drift`，**跳过不覆盖**
- 本地也改了 → 报告 `conflict`，退出码 3
- 加 `--force` → 覆盖，并在结果中标记

没有这道闸，这个工具会静默吃掉同事的手工修正，不报错、不告警。

### 破坏性护栏（防误删远端内容）

远端文档**没有可用的回滚手段**，所以凡是可能大规模抹掉远端内容的操作，默认一律拦截、要人显式授权。

| 触发条件 | 拦的是什么 |
|---|---|
| 远端块数 ≥ 3，且结果不到远端的一半，且有删除 | **本地被清空 / 被截断** —— 一次误操作、一次失败的生成脚本，远端整篇就没了 |
| 首次纳管一篇已存在的远端文档，且会改写其中任何块 | **与同事手工维护的文档重名** —— 第一次同步就把人工内容整篇替换成本地版本 |

**判据是「结果缩水」，不是「删了多少」。** 一开始我用的是「删除数超过一半就拦」，结果把正常编辑也拦了：一篇只有 1 个块的文档，改一改那段话就是 100% 删除比例。

| 情形 | 远端 | 结果 | 判定 |
|---|---|---|---|
| 本地被清空 | 5 | 0 | 拦 |
| 本地被截断 | 20 | 3 | 拦 |
| 误纳管同事文档 | 4 | 1 | 拦 |
| 全量重写 | 3 | 4 | 放行 |
| 删掉一段 | 8 | 7 | 放行 |
| 改一段话 | 1 | 1 | 放行 |

`--dry-run` 会预告这类变更，所以演练是有效的；确认无误后加 `--allow-destructive` 强制执行。

**另外两处防御**：破坏性判定依赖统计出的删除数，代码里有一道**内部不变量断言**（统计值必须等于变化段之和），对不上就中止 —— 否则护栏会「看着过了」而删除照常发生。`pull --write` 也不会覆盖本地已存在的同名文件（那可能是被 `exclude` 排除、从未纳入同步的文件）。

### 排查：把一次真机运行记录下来

工具的行为建立在若干条**无法在本地证伪**的假设上。要留一条把真机行为变成可复查证据的通路：

```bash
FWS_RECORD=/tmp/fws-run.jsonl fws sync --dry-run
```

依次记录每一次 API 交互（JSON Lines）。**请求头一律不记录，token 与 app_secret 脱敏但结构保留**，所以这份文件既安全、又能当夹具用。崩溃也不丢（同步追加），写不进去会出声（静默失败比不录制更糟）。

> 录制文件含文档正文，按敏感数据处理。

遇到对不上的行为，跑一次带 `FWS_RECORD` 的命令，把文件交给维护者即可定位。

### 与 git 的对应关系

`fws pull` 把「远端 vs 本地」的关系按 git 的语义分类：

| 状态 | git 类比 | 含义 |
|---|---|---|
| `in-sync` | up to date | 两侧一致 |
| `local-only` / `local-ahead` | 本地有新提交 | 待 `sync` 推送 |
| `remote-only` / `remote-ahead` | 远端有新提交 | 待 `pull --write` 拉取 |
| `conflict` | 两边都改了 | **人工合并**，工具不自动处理 |
| `roundtrip-diff` | ——（本工具特有） | 两侧都没改但渲染不出原样 |

**merge base 就是账本**：里面存着上次同步时的 `local_sha256` 与 `remote_revision_id`。两个锚点一比对就知道是谁改的，不需要额外的版本历史。

**「提交前先拉取」** 靠 `pull` 的退出码实现：

```bash
fws pull && fws sync
```

`pull` 一旦发现远端有别人改过就返回 3，`&&` 自动挡住推送。

**往返保真度**是这套机制的前提：远端块 → Markdown → 远端块 必须无损，否则每次对比都会看到假差异。`roundtrip-diff` 这个状态就是它的度量 —— 那类文档含飞书特有块（高亮块、画板、分栏），用 `pull` 覆盖本地只会把内容降级掉，应当**只推不拉**。

### 限流

飞书对块写操作有三层限制，缺一层就会在生产上撞 429：

1. 单应用写类 **3 次/秒**
2. 单篇文档并发编辑 **3 次/秒**（跨该文档所有写操作）
3. 服务端 `x-ogw-ratelimit-reset` 要求的**全局暂停**

第 2 条最容易漏：只做全局限流的话，单篇文档内部频繁改写仍会撞限流。

**定时频率要按文档规模算。** 稳态下一篇文章 1 次读请求；1000 篇每天一轮 ≈ 3 万次/月（安全），每 5 分钟一轮 ≈ 864 万次/月（超免费配额 8 倍）。

## 能力边界

| 期望 | 支持 | 说明 |
|---|---|---|
| 更新同名文档内容 | ✅ | |
| URL 不变 | ✅ | `node_token` 不动 |
| 未变块评论保留 | ✅ | |
| 改动块评论保留 | ✅ | 走 `batch_update` |
| 本地新增 → 远端建文档 | ✅ | upsert |
| 本地删除 → 远端处理 | ❌ | 本地已删除的文件**不会被处理**，远端文档原样留着，成为孤儿节点 |
| 本地重命名 | ⚠️ | 通常会在远端新建一篇，旧节点成为孤儿。要保住原节点需用 `aliases` 手工认领（见下） |
| 目录层级镜像 | ❌ | `nesting: mirror` 未实现，行为等同 `flat` |
| 生成飞书特有块 | ❌ | convert 不支持 Callout / 画板 / 分栏；且人工插入的这些块在同步时会被判为「远端多出来的块」 |
| **远端 → 本地拉取** | ✅ | `fws pull`，把远端渲染回 Markdown 并与本地按 git 语义比对 |
| **自动合并冲突** | ❌ | 两侧都改过的文档只报告、不自动合并 |
| **远端图片下载到本地** | ✅ | `pull --write` 下载到 `assets/<文档名>/` 并改写链接；账本已有的复用不重下 |

### 尚未实现的两项（配置里写了会直接报错）

这两项在设计里规划过，**代码里没有**。它们会在配置加载阶段被**拒绝**（退出码 2），而不是静默失效：

| 配置项 | 想要的效果 | 实际行为 |
|---|---|---|
| `nesting: mirror` | 把目录层级镜像成知识库子节点树 | 拒绝。全部平铺在 `parent_node_token` 下 |
| `on_delete` / `archive_node_token` | 本地删除时加 `[已废弃]` 前缀并归档 | 拒绝。本地删文件后不处理，远端文档原样保留 |

**为什么是拒绝而不是忽略**：配了不生效比报错更糟 —— 用户以为有层级、以为删除会被处理，
而系统不报错、不告警，等发现时知识库结构已经乱了。`nesting: flat` 例外，它与当前行为一致，允许保留。

> 远端节点无法真删除，是因为飞书**没有确认存在的「删除知识库节点」API** —— 调研时试了多个路径都是 404。
> 所以即使将来实现 `on_delete`，也只能做「标记归档」。

**本地重命名怎么补救**：在 `.feishu-sync/ledger.json` 的 `aliases` 里加一条 `"新路径": "原 node_token"`，
下次同步就会认领回原节点，而不是新建。也可以直接手工编辑账本里的路径键。

### 本地预检（写入前就拦下）

飞书的两条硬限制在本地提前检查，让失败发生在我们能说清原因的地方，而不是远端写到一半才报一个看不懂的错误码：

| 限制 | 超限时的行为 |
|---|---|
| 单文档块数 ≤ **20000** | 转换后立即拒绝，提示「请拆分后再同步」（否则远端报 `1770004`） |
| 单次插入 ≤ **1000** 块 | 提示「请把该文档拆小」（否则远端报 `1770006`） |

### 配额提醒

块级增量**并不比全量替换省调用量**（都是 1 update/delete + 1 convert + 1 descendant），它的价值纯粹是**保评论**。真正的省钱手段是快路径：正文与图片都没变时，每篇只花 1 次读请求。

素材上传有 **10000 次/天** 的硬限。账本会记录已上传的图片素材 token，路径与内容哈希都没变时跳过上传 —— 图多的库必须依赖这个。

### 两层测试

**第一层：内存版飞书**（`fake-feishu.ts` + `syncer.test.ts`）替换 `WikiApi`/`DocxApi`/`MediaApi` 这些**类**，用来验证同步逻辑本身。它模拟了三条关键服务端行为：**revision 自增**、**按索引范围删除**、**按 index 插入** —— 「索引不错位」这条判据靠它守住。它也是唯一能廉价验证「重复运行零写入」「改动块保留 block_id」这类幂等性质的手段。

**第二层：真实 HTTP 服务器**（`fake-feishu-server.ts` + `cli.e2e.test.ts`）把同一套状态暴露成 HTTP 接口，然后**以子进程方式运行真实的 CLI**。

第二层存在的理由很具体：第一层替换掉的是 API 类，所以 `FeishuClient` 完全没被覆盖 —— URL 拼接、鉴权头、响应包结构、请求体字段名这些**最容易写错**的地方是盲区。第二层的服务器会主动拒绝这些错误：缺 `Authorization` 头、用错 HTTP 方法、请求体缺必填字段、把只读字段（`merge_info`）传回来。

它已经抓到过一次真实问题：鉴权端点的响应结构与其它接口不同（token 在**顶层**，不包在 `data` 里），以及客户端把「取 token 失败」误当成网络错误退避重试 5 次、白等 30 多秒才报一个指向网络的错误。

`_research/` 存在的原因是**本工具尚未对真实飞书接口验证过**。真机联调时撞上「字段名写错了」或「错误码看不懂」，这份快照是唯一不依赖网络、不依赖应用权限的查证手段 —— 代码注释里每条「官方确认」的限制都能在其中查到出处。

系统性地关闭这些未知项走 `fws doctor`（见上文），它把每条假设变成一次真实调用；`_research/` 则用于解释「为什么代码是这么写的」。

它体积偏大是因为飞书的 API 文档页会把整套块结构 schema 在每个子操作里重复一遍，单个页面就能有 600KB。**待真机验证通过、事实固化进测试之后，这份快照就可以整体删除。**
